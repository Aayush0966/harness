  "analysis": "The core challenge lies in building a distributed rate limiter that is globally consistent yet highly available, performant, and resilient to network partitions, especially across AWS regions. Traditional centralized approaches (e.g., a single Redis cluster) would introduce significant latency and a single point of failure. Conversely, purely decentralized approaches risk allowing more requests than permitted during network partitions. We need a hybrid approach that leverages local enforcement for low latency and high availability, combined with a mechanism for eventual global consistency and coordination.\n\nKey considerations:\n1.  **Latency:** Rate limiting decisions must be made in sub-millisecond timeframes at the edge.\n2.  **Consistency:** While immediate global consistency is impossible without unbounded latency, we need 'eventual consistency with bounds'. This means that during a partition, a user might temporarily exceed their global limit but should be reined in once the partition resolves.\n3.  **Availability:** The rate limiter must remain operational even if one or more regions experience issues or network partitions.\n4.  **Scale:** 50,000 req/sec total, distributed across 3 regions means approximately 16,666 req/sec per region on average. Per-API key limits range from 100 req/min (1.67 req/sec) to 50,000 req/min (833 req/sec).\n5.  **Failover:** Graceful handling of regional outages for both the rate limiting service and its underlying data stores.\n6.  **Cost:** An enterprise-grade solution should be cost-effective.",
  "solution": "Our proposed solution utilizes a multi-layered approach combining edge enforcement, regional coordination, and global eventual consistency.\n\n**1. Data Store:**\n*   **Primary Regional Data Store:** AWS DynamoDB Global Tables. Each region will have a DynamoDB table for rate limit counters. Global Tables provide active-active replication across regions with strong eventual consistency. This means updates made in one region are asynchronously replicated to other regions, typically within seconds. This is suitable for our 'eventual consistency with bounds' requirement. We will store API key, current request count (per time window), and last updated timestamp.\n*   **Edge Cache/Local Enforcement:** AWS ElastiCache for Redis (cluster mode enabled) in each region. Each API Gateway/service will query this local Redis instance for the current rate limit status of an API key. This provides sub-millisecond lookup latency. Redis will act as a 'hot cache' and also be responsible for local incrementing and decrementing of the token bucket/leaky bucket counters.\n\n**2. Failover Strategy:**\n*   **Regional Failover (Data Plane):**\n    *   **API Gateway/Load Balancer:** Use AWS Route 53 with latency-based routing to direct traffic to the closest healthy regional API Gateway (or Application Load Balancer). Health checks will monitor the availability of the entire regional stack.\n    *   **Redis:** ElastiCache for Redis Cluster is highly available within a region, with automatic failover to replicas. If an entire Redis cluster fails, the API Gateway/service would fall back to querying DynamoDB directly (with higher latency) or, during a major regional outage, Route 53 would direct traffic to another healthy region.\n    *   **DynamoDB Global Tables:** Provides built-in multi-region active-active replication. If one region's DynamoDB becomes unavailable, other regions continue to operate independently. The global table ensures data integrity and eventual synchronization once the region recovers.\n*   **Regional Failover (Control Plane/Orchestration):** Our rate limiting logic (Lambda functions, ECS services) would be deployed in each region. Route 53 health checks ensure traffic only goes to healthy regions.\n\n**3. Edge Routing Mechanism:**\n*   **AWS Route 53 with Latency-Based Routing:** Clients will make requests to a single, global endpoint (e.g., api.example.com). Route 53 will resolve this to the IP address of the API Gateway (or ALB) in the geographically closest and healthy AWS region. This ensures requests hit the nearest edge for minimal latency.\n*   **AWS API Gateway (or ALB + EC2/ECS/Lambda):** The API Gateway will be the entry point for API requests in each region. It will integrate with a custom authorizer (e.g., Lambda) to perform the rate limiting check.\n\n**4. Rate Limiting Algorithm & Logic (Token Bucket with Distributed Synchronization):**\nEach API Gateway custom authorizer (e.g., AWS Lambda) will execute the following logic:\n\n1.  **Local Check (Redis Cache):**\n    *   Upon receiving a request for `API_KEY`:\n        *   Query the local ElastiCache for Redis for the current token count for `API_KEY` within the current time window (e.g., `api_key:tier:timestamp_minute`).\n        *   If tokens are available, decrement the counter in Redis and allow the request. Return a 'Rate-Limit-Remaining' header. This is the fast path (sub-millisecond).\n        *   If no tokens are available, reject the request with HTTP 429.\n2.  **Asynchronous Synchronization (DynamoDB & Local Replenishment):**\n    *   **Periodic Background Sync:** A background process (e.g., Lambda invoked by CloudWatch Events or an ECS task) in each region periodically (e.g., every 5-10 seconds) reads the *local increments* from Redis for active API keys and batches these updates to the regional DynamoDB table. It performs an atomic update on DynamoDB to add the local increments to the global counter for that API key.\n    *   **DynamoDB Streams & Cross-Region Updates:** DynamoDB Streams are enabled for each regional table. A Lambda function (or ECS task) in each region subscribes to the *streams of other regions*. When an update occurs in `us-east-1`'s DynamoDB, the `eu-central-1` and `ap-southeast-1` Lambdas are notified. They then update their *local Redis token counts* based on the global state in DynamoDB. This is the 'eventual consistency' part.\n    *   **Token Replenishment:** Each region's background process or a dedicated Lambda will also be responsible for replenishing tokens in Redis for API keys based on their tier, using the global state from DynamoDB as the source of truth. This prevents 'unbounded lock contention' by letting each region manage its own token bucket locally based on the shared global 'budget'.\n\n**Handling Network Partitions & 'Eventual Consistency with Bounds':**\n*   **During Partition:** If a region (e.g., `us-east-1`) gets partitioned from others, its local Redis will continue to serve requests based on its last known global state and local increments. It will accumulate its local usage in DynamoDB, but these updates won't immediately propagate to other regions. This means `us-east-1` might temporarily allow more requests than its 'fair share' if other regions are also allowing requests. However, users will not experience service interruption in `us-east-1`.\n*   **Post-Partition Resolution:** Once the partition is resolved, DynamoDB Global Tables will automatically sync all accumulated updates. The regional Lambdas subscribed to DynamoDB Streams will then update their local Redis caches, effectively 'reconciling' the global state. API keys that over-used during the partition will see their token counts drastically reduced (or set to zero) until their next replenishment cycle, effectively 'paying back' their overage.\n\n**Advantages:**\n*   **Sub-millisecond latency:** Local Redis cache at the edge ensures fast rate limiting decisions.\n*   **High Availability:** Each region operates independently, with DynamoDB Global Tables providing strong availability even with regional failures. Route 53 ensures traffic is routed to healthy regions.\n*   **Scalability:** DynamoDB and ElastiCache for Redis are highly scalable services. The distributed nature allows for horizontal scaling across regions.\n*   **Graceful Partition Handling:** Local enforcement continues during partitions, preventing service outages, with eventual reconciliation.\n*   **No Unbounded Lock Contention:** Local operations on Redis don't require cross-region locking for every request. Synchronization is asynchronous and batched.\n\nThis architecture provides a robust, high-performance, and resilient distributed global rate limiter that meets the specified requirements."
